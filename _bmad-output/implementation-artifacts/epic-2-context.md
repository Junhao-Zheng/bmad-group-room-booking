# Epic 2 Context: 完成预约并管理自己的安排

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

让课题组成员完成预约、确认重试结果、查看个人安排及取消，并允许管理员说明原因干预。通过占用互斥、授权和原子审计，使网络异常、并发请求及取消竞争仍产生明确且可追溯的结果。

## Stories

- Story 2.1: 提交有效且不冲突的活动预约
- Story 2.2: 确认重复提交和网络重试结果
- Story 2.3: 查看自己的预约及状态
- Story 2.4: 取消本人尚未开始的预约
- Story 2.5: 管理员说明原因干预未结束预约

## Requirements & Constraints

- 新预约直接生效；活动名、用途去首尾空白后分别为 1—80、1—500 字符，人数为正整数且不超过提交时容量。北京时间同日、整点或半点，满足 `t < start < end <= t+30天`，时长 30 分钟至 4 小时；结束为次日零点也拒绝。半开区间允许首尾相邻，同室预约与停用共同互斥。
- 状态优先判取消，否则按开始、结束边界派生待开始、进行中、已结束。个人记录按开始时间及标识降序；完整详情仅本人或管理员可读，他人及不存在记录统一 404。不得修改预约业务字段或硬删除历史；调整须取消后新建。
- 成员首次取消限本人且 `t<start`；管理员首次干预限 `t<end`，原因去空白后 1—500 字符。先授权、校验管理原因，再判断重复取消；重复返回原操作者、时刻、原因，不产生新转换。管理员使用本人取消入口仍按成员规则。
- 成功意图按成员隔离并长期保留；重放返回原预约当前状态，失败不占标识。相同标识变更实质业务字段返回 409，显示名变化不影响比较。
- 验收使用真实文件库与独立 HTTP 会话：20 人争用同槽须 1 成功、19 冲突；同意图并发 20 次须同一编号及一次创建审计；成员与管理员取消竞争至少 20 轮，仅一次转换。审计故障须完整回滚，重启须保留记录及意图；保存原始结果，不能用锁超时替代规定冲突。

## Technical Decisions

- 沿用 Flask/Jinja 分层单体与 SQLite；服务为唯一业务写入口，操作者来自会话。写入使用独立连接和 `BEGIN IMMEDIATE`，取锁后复核会话、角色、所有权，并从统一 `Clock.now_epoch()` 取得一次时间。所有 POST 检查精确 Origin 与 CSRF。
- 预约和停用共用 `reservations`；`occupancy_slots(room_id,slot_start)` 唯一，槽长 1800 秒。有效记录必须拥有完整槽，取消清空槽，已结束未取消记录保留槽。业务、槽、审计同事务；命令只调用一次 `audit_writer(conn,event)`，重放/重复取消零次，writer 不另开事务。记录操作者快照、对象、时刻、前后值及适用原因。
- UTC 整数秒存储；输入严格为北京时间 `YYYY-MM-DDTHH:MM`，不接收偏移或秒。JSON 人数及 ID 仅接受整数而非布尔/浮点/数字字符串，ID 限正 64 位；文本按 Unicode 字符计数，拒绝 NUL 和无效 UTF-8。只有测试可注入时钟与故障 writer。
- 意图标识为 16—80 位 `[A-Za-z0-9_-]`，新表单生成随机标识。规范化并持久比较房间、名称、用途、人数、UTC 起止六字段；成功重放必须早于新时间窗口、容量及占用检查，确保取消、开始或降容量后仍可重放。
- 服务返回领域 DTO，web 只包装一层 `ok/data`。创建结果为 `booking/replayed`，新建 201、重放 200；本人/管理员使用完整白名单，普通成员冲突信息不能泄露他人用途、人数、账号或取消原因。字段错 400、认证 401、权限 403、合并不存在 404、业务冲突 409、锁超时 503、内部失败 500；错误不泄露 SQL、堆栈或凭证。

## UX & Interaction Patterns

沿用中文布局与北京时间提示。提交中禁用按钮；成功显示编号及时段；冲突保留输入，响应未知时沿用原意图重试，实质编辑才换标识。个人列表突出活动、房间、时段和四态；取消须确认，管理干预还需原因。取消后刷新列表与可用性；会话失效不自动重提。控件有标签、焦点及文字反馈，用户文本安全转义；桌面与 390px 手机无页面横向溢出。

## Cross-Story Dependencies

依赖 Epic 1 的认证、目录、共享日程及可用性查询；本史诗按 2.1→2.2→2.3→2.4→2.5 推进。与 Epic 3 共用占用及容量事务规则，后续联验创建对停用/降容量竞争。2.5 是实验 A 的 X 组，保留首次实现快照；与停用撤销保持独立命令，不能提前实现对照故事。综合审计与重启验收依赖 2.5 完成。
