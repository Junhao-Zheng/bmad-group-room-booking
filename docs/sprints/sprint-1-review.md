# Sprint 1 增量评审与复盘

性质：同一天压缩实施的真实增量；AI主流程记录，不冒充真实小组会议或教师M3验收。原计划7个故事：1.1、1.2、1.3、2.1、2.2、2.3、2.4。范围未因实验B豁免而省略成员取消。

## 目标与评审

本轮目标已实现：成员可以登录、查找时段、创建预约、确认不确定提交、查看本人记录并在开始前取消。7个故事已按实际事件逐一完成，2.3清理返工也已闭环。代码接受提交为 `b8069f377f17fdd83796ad06c4b6ce07091b891d`，最终121个唯一Python测试、86项JS及新功能真实HTTP/双视口浏览器通过。初稿、失败、评审分类及修补后证据都保留。

评审演示采用独立合成账号和临时数据库。真实用户尚未试用；“测试通过”仅代表所定义断言通过。涉及管理员干预的需求保留至第二轮及实验A，不提前用通用完成函数实现实验目标。

## 已观察的问题与改进依据

- 认证、创建和查询的边界需要在服务内部复核，页面隐藏按钮不能保障权限。后续管理命令继续在写锁后取一次Clock和当前会话角色。
- 网络响应丢失不能被当作创建失败。重试的当前结果、原意图是否确认和已知预约编号必须分别表达；相关实际修复与浏览器断网证据在2.1/2.2评审记录。
- 测试自身可能掩盖问题，例如同时改多个字段使单字段签名错误未被发现。第二轮继续按边界/原因逐项独立断言，并让独立验证层检查未覆盖行为。
- 结果文件不能在失败重跑后沿用旧PASS。浏览器与性能证据按run_id隔离，先发布INCOMPLETE，成功且清理后才标PASS；工具传输失败独立于产品缺陷登记。
- 前端键盘焦点、长文本和已失效页面不能只靠单元测试判断，仍须用桌面/手机真实浏览器核对。

## 第二轮可执行行动

1. 所有管理写入验证writer前/后故障、槽与业务原子性、角色变化和精确截止边界。
2. 完成预约/停用及预约/降容量两种双请求竞争，每类20轮，用数据库最终事实判定。
3. 在实验初始实现前冻结共同基线、上下文清单和同一评审表；封存两组初稿后再修复，负结果照实报告。
4. 最终复盘从实际build-metrics和story-events生成；人工日志、教师门禁和真实试用缺口保持明确。
